# ADR-0013: Universal search, per-task model tiering, vision attachments, and a per-org budget

Status: Accepted

## Context

Live testing surfaced a real capability gap: no department can do open-ended research (a market-research goal got routed to `product_analytics`, which is scoped only to internal task/SLA metrics and correctly declined it — but the decline reason was itself invisible until a separate fix). At the same time, the fixed 500/day Gemini budget from ADR-0012 was found to risk blocking a live demo outright, with no way to raise it short of a redeploy. The user asked for all of this together: real web search on every agent, automatic cost-aware model selection, vision input, and a frontend-configurable budget. These four are grouped in one ADR because they were designed and shipped together and share one constraint: every department's `LlmAgent`(s) are built once at import time as module-level singletons, not per-request — several of the decisions below exist specifically to work within that constraint rather than around it.

## Decision

**Universal search.** `google.adk.tools.google_search_agent_tool.create_google_search_agent()` + `GoogleSearchAgentTool` — ADK's own documented workaround for combining the built-in `google_search` grounding tool with custom function tools on the same agent — is instantiated once in `app/adk_agents/factory.py` and appended to `_CEO_TOOLS` and `_DEPARTMENT_UNIVERSAL_TOOLS`. Every department and the CEO get it automatically through the existing `department_tools()`/`build_ceo_agent()` plumbing; no per-department wiring was needed.

**Per-task model tier, CEO-decided.** `create_task` gains `model_tier: Literal["flash", "pro"] = "flash"`, stored on `Task`. Because department agents are singletons, mutating `.model` per-turn would race across concurrent orgs on Cloud Run — instead, `factory.py`'s new `build_tiered_stage_agents()` builds **two** singletons per pipeline stage (flash and pro), and each department's `on_task_received` indexes `stage_agents[task.model_tier]`. The tier applies uniformly across every stage of a task's pipeline run, decided once by the CEO when it creates the task — no extra LLM call, since the CEO already judges task complexity when decomposing a goal. `sales_crm`'s `SequentialAgent` (the one department that can't swap `sub_agents` per call) builds two full pipeline singletons instead of two per-stage ones; its A2A `root_agent` (external callers never set `model_tier`) is pinned to the flash-tier pipeline.

**Vision, via Cloud Storage.** Images are uploaded once to a GCS bucket (`app/services/storage_client.py`, the only module allowed to import `google.cloud.storage`, mirroring `firestore_client.py`'s convention) and referenced by `gs://` URI on `Task`/`Message` — never stored as base64 in Firestore, which would have hit the 1MiB/doc limit around ~700KB of actual image data. `google.genai.types.Part.from_uri()` lets Vertex AI Gemini read the GCS object directly at inference time, so the backend never re-downloads or re-encodes it. The image reaches the CEO's own turn directly (stashed via `store.set_ceo_pending_attachment`) and is pulled onto every task `create_task` creates by default (`include_attachment: bool = True` — a human dispatch is usually about one thing; the CEO can pass `False` for a task it knows is unrelated). Each department's first pipeline stage is the only one that ever sees it — later stages work from that stage's text output, same as today's text-only flow — except `legal_risk`, `executive`, and `product_analytics`, whose inputs are synthesized text/JSON with nowhere sensible for an image to land, so they don't wire it at all.

**Per-org configurable budget.** `orgs/{orgId}/settings/config.dailyGeminiCallLimit` (via new `store.get_org_settings`/`update_org_settings`, following the existing `org_doc` pattern) overrides `settings.corporate_daily_gemini_call_limit`, which changes role from "the cap" to an ops-level fallback used only when an org hasn't set its own — raised from 500 to 5000 so it stops being a demo-blocking default while still catching a genuine runaway loop. `run_agent_turn` resolves `store.get_org_settings(org_id).daily_gemini_call_limit or settings.corporate_daily_gemini_call_limit` before the existing atomic-counter check from ADR-0012, which is otherwise unchanged. A new `GET`/`POST /api/org/{org_id}/settings` (auth-covered automatically by the existing router-level `require_org_member` dependency) and a frontend Settings tab let a user actually change it without a redeploy.

## Alternatives considered

- **Base64-in-Firestore for attachments**, per the original draft of this ADR. Rejected once the ~700KB effective ceiling (after base64's ~33% inflation, under Firestore's 1MiB/doc limit) was flagged as too low for real screenshots/photos — GCS + `Part.from_uri` removes the ceiling entirely and turns out to be the more natural Vertex AI integration anyway (no manual download/re-encode round trip).
- **A deterministic priority→tier rule** (task priority 1–2 → pro, 3–5 → flash) instead of letting the CEO decide. Rejected — fully predictable but not "automatic" in the sense asked for, and priority already means something else (urgency, not complexity); would need a second field regardless.
- **`include_attachment` defaulting to `False`** (opt-in per task). Rejected after re-reading the intended behavior against the literal code default — an LLM asked to remember an optional flag on every `create_task` call is exactly the kind of thing that gets silently dropped; defaulting to `True` matches "attaches to everything unless told otherwise" without relying on the CEO proactively opting in every time.
- **Fully unlimited budget by default, no global fallback at all.** Rejected — a genuine runaway loop (a message ping-pong bug, not just cost-consciousness) would have nothing stopping it until someone noticed the bill; a high (5000/day) fallback is invisible for any realistic demo but still a real backstop.
- **Mutating a shared singleton's `.model` per-turn** instead of building two tiers. Rejected outright — a real race condition the moment two orgs' turns for the same department overlap on Cloud Run, not a hypothetical.

## Consequences

Every department gets search and tiering through the same two shared helpers (`factory.py`'s tool list and `build_tiered_stage_agents`) with no bespoke per-department logic beyond the mechanical `agents[tier]` indexing — a new department gets both for free by following the existing `build_tiered_stage_agents(...)` pattern instead of constructing `LlmAgent` directly. The tradeoff is roughly double the `LlmAgent` object count at import time (up to ~4 stages × 2 tiers × 9 departments) — pure object construction, no added network cost, not expected to matter at this scale. Vision attachments add one new GCP resource (a bucket) and one new IAM grant (Vertex AI's service agent needs `storage.objectViewer` on it) to `infra/deploy/setup.sh`. The budget change means `corporate_daily_gemini_call_limit` in `.env`/`app/config.py` is no longer *the* cap for any org that has configured its own — anyone reading ADR-0012 alone would miss that; this ADR is the record of that shift.
