# ADR-0016: Agent capability expansion — per-department integration access, org knowledge base, sub-agent spawning, sandboxed multi-tool orchestration

Status: Accepted

## Context

The office-floor/layout overhaul (frontend) surfaced a set of real platform questions with no answer yet: how does an org customize what an agent knows or can reach, how does a user control which department can call which third-party integration (and what happens when an agent needs one it doesn't have), can an agent delegate a genuinely separable sub-task instead of doing everything inline, and can an agent combine several of its own tool calls into one round trip instead of N. Real research into Anthropic's Programmatic Tool Calling (Claude-API-specific, Anthropic-hosted code containers) and "speculative PTC" (requires raw partial-token-generation access) confirmed neither is usable against this Gemini-via-Vertex-AI-only, ADK-`Runner.run_async` stack — the same eligibility constraint that shaped ADR-0002/0014. What's genuinely portable — letting an agent orchestrate several of its own tool calls in one snippet instead of many round trips — is reimplemented natively below.

## Decision

1. **Per-department integration access control** (`Integration.connected_departments`, already on the model and already written by the create-integration form, previously dead/unread). `call_integration` (`integration_broker.py`) now takes a required `department_id` and enforces the allowlist — empty means unrestricted, matching every pre-existing integration's behavior exactly, zero migration. A denial raises `IntegrationAccessDenied(ValueError)`, a subclass so both existing fail-soft call sites (`notify_slack_channel`, `create_jira_ticket`) need no changes. Denial also files a standing `orgs/{orgId}/access_requests/{id}` doc (not a task-blocking flow — a permission decision is an org-admin-timescale call, not a per-task one) that an owner resolves via `app/api/access_requests.py`, the first real use of `require_role("owner")`. The frontend's Settings tab gained a real "Connected apps" panel (per-integration, per-department toggles) and a pending-requests panel.
2. **Org-uploadable knowledge base** (`orgs/{orgId}/departments/{departmentId}/knowledge_base/{docId}`, reusing the already-reserved `departments` collection name from ADR-0003's list). `department_kb_text(org_id, department_id, static_fallback)` joins uploaded docs verbatim, falling back to the existing static corpus (`HR_HANDBOOK`, `customer_support`'s per-intent `KNOWLEDGE_BASE`) when nothing's uploaded — a fresh org behaves identically to before. `hr_people_ops` and `customer_support` each swap one line. No embedding/search: the static corpora were never searched either (inlined whole into the prompt), so there's nothing for a vector index to improve on yet.
3. **Sub-agent spawning**, reusing the existing ephemeral `spawn_worker` mechanism rather than reversing ADR-0004's Pub/Sub-only CEO↔department boundary. `spawn_worker_and_await` (`workers.py`) is a synchronous sibling with a 120s timeout that returns the worker's real result inline. `spawn_subagent_tool` (`universal.py`) is wired only to `_CEO_TOOLS` and two departments' `extra_tools` (`engineering_sre`, `product_analytics`) — critically **never** to `_DEPARTMENT_UNIVERSAL_TOOLS`, which the ephemeral worker agents themselves also use. A spawned worker therefore cannot itself spawn a worker: depth-1 by construction, not by a counted-and-rejected limit.
4. **Sandboxed multi-tool orchestration** (`execute_python_tool`, wired to the CEO and `product_analytics`). A real OS subprocess (`python -m app.services.sandbox_runner`) is the actual isolation boundary — only a real process can be `kill()`ed regardless of what's running inside it (a bare in-process `exec()` with a builtins allowlist can't stop a `while True`, and Python threads can't be force-killed). `RestrictedPython.compile_restricted` runs inside that subprocess as defense-in-depth on top, closing the `().__class__.__bases__` gadget a builtins allowlist alone can't. The child never imports `app.services.store` or holds any credential; a whitelisted `call_tool(name, **kwargs)` call is serviced over a line-delimited JSON stdio protocol by the parent (`sandbox.py`), which is the only side with real org/agent context. Tool allowlist v1 is read-only (`list_tasks_tool`, `list_agents_tool`, `search_memory_tool`, `read_memory`) — write tools stay individually visible in the outer turn's own trace/audit log rather than proxied opaquely through a snippet.

## Alternatives considered

- **In-process `exec()` with a builtins allowlist, no subprocess** — rejected outright; empirically confirmed (via a direct probe, not assumed) that RestrictedPython alone still can't bound wall-clock time for a `for`-loop-free `while True`, and that a real subprocess `kill()` is what actually terminates one (verified live: a `while True: pass` snippet ran for the full timeout and was killed by the parent, not by anything inside the sandbox).
- **Task-blocking (`TaskStatus.BLOCKED`) for integration access denial**, mirroring `_ask_human` — rejected. The existing integration call sites are deliberately fail-soft (a missed Slack ping doesn't invalidate the incident task itself); routing a permission-governance decision through the task-blocking path would conflate two different timescales.
- **Embedding-and-searching the knowledge base** like `write_memory`/`search_memory_tool` — rejected for v1; the static corpora it replaces were never searched, only inlined, so there's no real gap this would close yet.
- **A per-turn sub-agent depth counter** instead of structural exclusion from `_DEPARTMENT_UNIVERSAL_TOOLS` — rejected; a counted limit can be gamed or miscounted, structural absence of the tool from the worker agents' own tool list cannot.

## Consequences

- ADR-0004 (A2A/Pub/Sub boundary) is unchanged — sub-agent spawning is additive to the existing ephemeral-worker mechanism, not a new delegation channel.
- `RestrictedPython==8.5` is the one new dependency introduced by this ADR, justified on security grounds (see Decision §4).
- The sandbox's read-only tool ceiling is a deliberate, documented (`ponytail:`) limit — extending it to write tools needs its own sandboxed-write audit design, not assumed here.
- `firestore.rules` needed no changes for either new collection (`access_requests`, `departments/{id}/knowledge_base`) — both already fall under the existing org-member-read/backend-only-write wildcard rule.
