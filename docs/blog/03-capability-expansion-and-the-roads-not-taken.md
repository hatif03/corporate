# Building Corporate, part 3: capability expansion and the roads not taken

*Part 3 of a four-part series on building Corporate. [Part 1](01-why-a-company-of-agents.md) and [part 2](02-departments-verification-and-the-things-that-broke.md) covered why I shaped this as a company of agents and the department/verification patterns underneath it. This part covers two deliberate research spikes that ended in "don't build this," and the capability expansion — sub-agent spawning, sandboxed code execution, realtime voice, OAuth connect, and a genuinely difficult correction — that followed.*

## Research digression: Google Antigravity, evaluated and rejected

[ADR-0014](../adr/0014-antigravity-rejected-curated-skills-instead.md): a request to make department agents feel like a real persistent, stateful multi-agent harness — not one-shot chatbot replies — led me to Google Antigravity: the `google-antigravity` SDK plus a separate `agy` CLI, the one other Google-only stack option available given this project's hard constraint. I didn't evaluate it from documentation. I installed the real package, inspected it with Python's `inspect` module against the actual installed source, and ran it against live Vertex AI turns.

Three independent blockers came out of that, not one:

1. A `protobuf` version conflict with the A2A SDK — resolvable, not disqualifying on its own.
2. **No pluggable persistence that survives a fresh process.** The real installed API had none of what the documentation described — no `BaseDb`, no `SqliteDb`/`PostgresDb` abstraction. The only continuation mechanism tied state to local disk. An ephemeral, scale-to-zero, multi-instance Cloud Run deployment cannot tolerate that — there's no guarantee two turns of the same conversation land on the same instance, or that the instance survives between them at all. The only way to inject history manually was reaching into a private, unsupported internal attribute on an early Alpha package. I rejected that as too fragile to build on days before a deadline.
3. The CLI's real headless auth path, once actually exercised, was a raw Gemini API key — not Vertex AI. That directly conflicts with this project's own hackathon eligibility requirement (Vertex AI, not a raw key).

I let Antigravity go entirely — no dependency, SDK or CLI, anywhere in the codebase. What shipped instead needed no new framework at all: curated, individually attributed excerpts from real MIT-licensed prompt-engineering skills, appended directly into the relevant department prompt files. And the investigation surfaced something better than a workaround — once I actually checked, department sessions already persist across turns via the existing `FirestoreSessionService`. The "no memory between turns" gap the whole investigation started from didn't actually exist; I'd been about to solve a problem I didn't have. Curating the skill excerpts also caught two real misfits (`security-guidance`, which is an editor hook, not domain knowledge an LLM turn can act on; `saas-metrics-coach`, whose ARR/MRR coaching doesn't apply to per-invoice review) and one misassignment (a revenue-operations skill fits lead qualification better than deal strategy) — corrected before they ever landed, not forced to fit because they were already in hand.

## Research digression: opencode, patterns adopted, framework rejected

[ADR-0015](../adr/0015-native-loop-hardening-from-opencode-patterns.md): a request to study a real, mature open-source coding agent — [`anomalyco/opencode`](https://github.com/anomalyco/opencode), MIT-licensed, source read directly via `gh api` — plus four outside sources on "loop engineering," led me to reimplementing several concrete patterns natively against my own ADK/Firestore stack, with zero new dependency:

- A doom-loop guard: the same tool called with byte-identical arguments three times in a row raises a `RuntimeError`, routed through the same `@audited_task` failure path every other department failure already uses.
- Session compaction — this resolved a risk I'd flagged earlier and deliberately deferred: Firestore documents cap at 1MiB, and a long-running agent session's event array will eventually hit that ceiling. I reworked compaction around Firestore's actual byte-size constraint, not a token-window estimate — the token window is the wrong metric here, since Gemini's context limit isn't what's actually at risk; Firestore's document size is.
- Gated memory auto-surfacing: a cheap existence check gates the real (more expensive) semantic-search call, so an agent with no memory yet costs nothing extra on the single hottest code path in the app.
- Extending the maker/checker verification pattern into two more departments, and closing one real gap a tool audit found along the way: a Jira integration template existed in the broker's catalog but nothing anywhere ever actually called it.

What I explicitly let go: opencode's in-process sub-agent/child-session pattern for CEO-to-department delegation. This one's worth explaining, because it's not a "not invented here" rejection — it's a real architectural mismatch. opencode's pattern assumes a single local process spawning child sessions in-process. Corporate's CEO-to-department delegation is Pub/Sub-based specifically *because* departments are conceptually separate services, not children of one process — adopting the pattern would mean rebuilding the exact thing [ADR-0003](../adr/0003-firestore-pubsub-for-state-and-messaging.md) already decided against. I also considered narrowing `spawn_worker`'s tool permissions, mirroring opencode's sub-agent permission-narrowing, and dropped it — there was no concrete evidence of an actual problem it would solve, just a pattern that looked prudent in isolation. And I declined to force `vote_aspects` onto every remaining department (Sales & CRM already has a deterministic guardrail elsewhere; Product & Analytics and the Office of the CEO both narrate deterministically-computed numbers with no external claim that could be mis-grounded in the first place) — the same "don't force a fit" principle from the Antigravity skill-curation above, applied again.

## What I actually built on top of all that: ADR-0016's capability pass

A UI review (see [part 1](01-why-a-company-of-agents.md)) surfaced real platform questions I hadn't answered yet: how does an org customize an agent, connect its own data, control which department can use which integration — and let an agent request access it doesn't have — and can agents spawn sub-agents or combine several of their own tool calls into one round trip? Full detail in [ADR-0016](../adr/0016-agent-capability-expansion.md).

The sub-agent question had a direct answer once I looked: reuse the existing ephemeral `spawn_worker` mechanism rather than reopening the Pub/Sub-only CEO-department boundary. A synchronous `spawn_worker_and_await` sibling with a 120-second timeout returns a delegated sub-task's real result inline, in the same turn. The depth cap here is **structural, not counted** — the new tool is wired only to the CEO and two specific departments, and deliberately excluded from the tool list the ephemeral worker agents themselves receive. A spawned worker cannot spawn another one, not because a counter stopped it at some limit, but because it was never given the tool to do so in the first place. I considered a per-turn depth counter and rejected it specifically because a counted limit can be gamed or miscounted; structural absence of the capability cannot.

The tool-combining question led to research into [Anthropic's Programmatic Tool Calling](https://platform.claude.com/docs/en/agents-and-tools/tool-use/programmatic-tool-calling) — fetched and read directly, not assumed — and confirmed **not usable**: it's a Claude-API-specific beta (Anthropic-hosted stateful code containers), and this backend is Gemini-via-Vertex-AI only, a hard eligibility requirement. A related "speculative PTC" idea (a token-stream-level inference-server optimization requiring raw partial-generation access) was equally confirmed not implementable against ADK's `Runner.run_async`. What was actually portable from that whole research thread — letting an agent orchestrate several of its own tool calls in one snippet instead of many round trips — got reimplemented natively as a sandboxed `execute_python` tool, the one real takeaway.

Building that sandbox meant rejecting two half-measures in sequence. A bare in-process `exec()` with a builtins allowlist was rejected outright — the classic `().__class__.__bases__` gadget chain defeats it, and a CPU-bound `while True` loop can't be force-killed in-process no matter what you strip from builtins. [`RestrictedPython`](https://pypi.org/project/RestrictedPython/) alone, still in-process, was also rejected as insufficient on its own — it closes the gadget-chain hole but still can't bound wall-clock time. What shipped is a real OS subprocess as the actual isolation boundary — only a real process can be `kill()`-ed regardless of what's running inside it — with `RestrictedPython`'s `compile_restricted` running inside that subprocess as defense-in-depth on top of the process boundary, not instead of it. I verified this live, not by reading the design and assuming it worked: a malicious `import os` snippet was rejected by the real subprocess; a `while True: pass` snippet ran for its full timeout and was actually killed by the parent process; a multi-lookup task completed in one real round trip instead of N. The child process never imports the store module or holds any credential — a whitelisted, read-only `call_tool()` surface is serviced entirely by the parent over line-delimited JSON on stdio. Write tools were deliberately left out of that allowlist, pending a real sandboxed-write audit design that doesn't exist yet — they stay individually visible in the outer turn's own trace log instead of being proxied opaquely through a snippet.

Alongside those: per-department integration access control (reusing a Firestore field that already existed on the model and was already being written by the create-integration form, but had never once been read — empty means unrestricted, non-empty is a strict allowlist, and a denial files a standing request for an owner to resolve rather than blocking the task itself, since a permission grant is a governance-timescale decision, not a per-task one), and an org-uploadable knowledge base per department that deliberately is **not** embedded or searched — the static corpora it replaces were never searched either, only inlined whole into the prompt, so there was nothing yet for a vector index to actually improve on.

## Voice, OAuth, and a genuinely difficult correction

Three more real features, each with its own ADR, landed after the capability pass above.

**Realtime voice** ([ADR-0017](../adr/0017-realtime-voice-websocket-relay.md)) came from studying a reference app's own voice feature — built on a different LLM provider's Realtime API — and asking whether Vertex AI has a genuine equivalent. Real research (installed-source inspection of [`google-genai`](https://pypi.org/project/google-genai/), not docs) confirmed yes: [`client.aio.live.connect()`](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api), GA since 2025-12-13, ADC-authenticated, no new provider needed. One hard constraint shaped the whole design: Vertex's Live API has no ephemeral-token path at all — the installed SDK raises `ValueError` outright if you try — so a browser can never safely hold the credential a Live session needs. A real backend-held WebSocket relay was the only legitimate architecture, not a corner cut for time. I scoped v1 deliberately narrow: a real voice *conversation* with the CEO's persona, not yet wired to its actual tools. Routing voice through ADK's `Runner.run_live`/`LiveRequestQueue` for real tool-calling was a real reference implementation I found in ADK's own installed source, but not something I independently verified line-by-line this pass — and shipping an unverified change to how the CEO's tools get invoked was a worse trade than shipping a smaller, fully verified voice feature.

**OAuth "Connect with X"** ([ADR-0018](../adr/0018-oauth-connect-flow.md)) replaced "paste a raw API token" with a real consent-screen flow for Slack, GitHub, and Notion. Real per-provider research found genuine transport differences — Slack and GitHub exchange an authorization code via a form POST with the client secret as a form field; Notion exchanges via a JSON body with the secret sent as HTTP Basic Auth — different enough that one shared OAuth helper would have needed provider-specific branches inside it anyway, so three small explicit adapters shipped instead of one generic abstraction pretending to be uniform. This surfaced a real pre-existing bug: the integration broker only ever attached an `Authorization` header for `BEARER`-type credentials; `OAUTH2` silently fell through with no header attached at all. Every OAuth-connected integration would have been silently broken had this gone unnoticed.

**Gemma, Veo, and Lyria** ([ADR-0019](../adr/0019-gemma-veo-lyria-vertex-ai-expansion.md)) is the one that didn't go as planned, and I think that's the more useful story to tell than a clean success. The [hackathon's own rules](https://allthingsagentichackathon.devpost.com/) call out Gemma/Veo/Lyria as bonus scoring, and I independently wanted a cross-model "second opinion" checker for runtime hallucination mitigation. Initial research (real docs, at the time) suggested all three were reachable the same way this project already reaches Gemini — fully managed Vertex AI endpoints, same ADC credentials, zero-deployment serverless access. Live-testing against real Vertex AI told a different story for one of the three: every Gemma variant — `gemma-3-27b-it` down through `gemma-3n-e2b-it`, and a newer `gemma4` visible in the Model Garden console — 404'd on a direct `generateContent` call, across every region I tried. The Model Garden console explained why: Gemma's card here shows only a "Deploy model" button — provision a dedicated, hourly-billed GPU endpoint — never the lightweight "Grant access" a true zero-deployment model would show. I tried real alternatives (Llama, Mistral, Codestral, Jamba) and every one 404'd the same way — this project's Vertex AI access has no third-party open-model serverless tier enabled at all, at any tier.

Self-hosting a dedicated GPU endpoint for one aspect checker, this close to a deadline, was a bad trade — real ongoing cost, real provisioning time, for a feature that's one checker among several. I shipped the independent-review checker anyway, just running on a distinct Gemini tier instead of Gemma. It's still a genuinely separate model call — fresh context, no shared state with the primary generation — the architectural value I wanted holds; it's just not a different vendor, and I said exactly that in the ADR rather than let the "cross-model" framing quietly stay technically inaccurate. Veo and Lyria, by contrast, were both confirmed fully live-working — including catching a real bug along the way: Lyria's actual response field name is `bytesBase64Encoded`, not `audioContent`, which a search-engine-summarized "verified" example online had gotten wrong. I only caught that by generating a real WAV file and checking it played, not by trusting a snippet that looked authoritative.
