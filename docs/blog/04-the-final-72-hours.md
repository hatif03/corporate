# Building Corporate, part 4: the final 72 hours

*Part 4 of a four-part series on building Corporate, and the last one. [Part 1](01-why-a-company-of-agents.md), [part 2](02-departments-verification-and-the-things-that-broke.md), and [part 3](03-capability-expansion-and-the-roads-not-taken.md) covered the shape of the system, the department/verification patterns, and the capability expansion with its research digressions. This part covers what happened three days out from the [hackathon](https://allthingsagentichackathon.devpost.com/) deadline, when a routine "get ready to submit" pass turned up one hard eligibility problem and one real, previously-unnoticed production bug — and what I did about both.*

## The ask that started it

With the app deployed and working, my next request to myself was broad on purpose: show more of what the agents are actually doing on the frontend, show the health of the deployed services, do a dedicated error-handling audit, build a real landing page, and — the part that mattered most in hindsight — run a complete pass on the app making sure it's used like it's intended to be used in production, find any errors and problems that arise in the working, find whether all services are being used as expected or the AI agents are ignoring something they're meant to use.

That last piece is doing the real work. It's not "does the demo look good" — it's "is anything actually broken that I haven't noticed because nobody's looked."

The first pass (landing page, error handling everywhere, service-health indicators, richer data on every view) went fine and shipped cleanly. It's the second pass — a fuller production-readiness audit, three days before the deadline — where things got interesting.

## Finding one: a hard eligibility gap, found by re-reading the actual rules

I fetched the hackathon's own rules page directly rather than working from memory of an earlier read. Buried in the required-technologies section: **"Gemini 3.5 or newer,"** for every track, no exceptions. Corporate's default model configuration was `gemini-2.5-flash` / `gemini-2.5-pro` / `gemini-2.5-flash-lite`. Below the floor, on every single department's reasoning.

This wasn't a "let's polish this eventually" item. It was a hard eligibility gate, three days before submission, on the model every agent in the entire app actually runs on.

I didn't trust documentation to tell me which model IDs would actually work — I'd already been burned once by exactly that with Gemma ([part 3](03-capability-expansion-and-the-roads-not-taken.md)). So: a direct `client.models.list()` call against this project's real Vertex AI access, not the Model Garden docs page. That confirmed `gemini-3.5-flash`, `gemini-3.5-flash-lite`, and `gemini-3.1-pro-preview` are genuinely reachable here (Gemini 3.5 Pro has no public model ID anywhere yet — I checked, independent web research at the time agreed). But a direct `generate_content` call to those exact IDs 404'd, at the same `us-central1` region every other model in this project already used successfully.

That could have meant real new plumbing — a second location setting threaded through the agent factory, a config change touching every department. Before writing any of that, I read the actual mechanism: [`google.adk.models.google_llm.Gemini.api_client`](https://github.com/google/adk-python)'s installed source shows it builds its Vertex client with no explicit `project` or `location` passed at all. Those get resolved from environment variables by [`google-genai`](https://pypi.org/project/google-genai/)'s own client — and reading *that* source showed something I didn't expect: when neither an explicit location nor `GOOGLE_CLOUD_LOCATION` is set, it silently defaults to Vertex's `global` endpoint. This project has never set `GOOGLE_CLOUD_LOCATION` — only an unrelated custom-named variable read solely by my own explicit client constructions elsewhere (Veo, Lyria, embeddings, voice). Every ADK-driven Gemini call in this app had already been resolving to `global` by default, the whole time, with nobody having configured it that way on purpose.

I confirmed this with a real end-to-end ADK agent turn — not a raw API call, the actual `Runner.run_async()` path every department uses — against all three candidate models, before changing a single line of production config. All three worked. Zero location-plumbing changes needed. Just the model ID strings. Full detail in [ADR-0020](../adr/0020-gemini-3.5-hackathon-eligibility-upgrade.md).

While re-verifying the voice model against the same live-testing discipline, I found it had quietly gone dead in production, independent of any of this: the previous `gemini-2.0-flash-live-preview-04-09` now 404s. Fixed with the same rigor — a real [`client.aio.live.connect()`](https://docs.cloud.google.com/vertex-ai/generative-ai/docs/live-api) round trip against the replacement before committing it.

## Finding two: a real production bug, found by auditing observability

Part of the audit was checking whether ephemeral workers' execution was actually visible anywhere in the frontend. Following that thread meant reading `update_agent_status` — the function every single agent turn calls at its very start, via `before_agent_callback` — closely enough to notice it does a Firestore `.update()` call. `.update()` throws `NotFound` if the target document doesn't already exist.

Ephemeral workers (`spawn_worker`, `spawn_worker_and_await`) use their own generated worker ID as their session ID, and the shared ADK callback mechanism treats session ID as agent ID for status/trace purposes. But a worker never gets a real `agents/{id}` document created for it — only registered department agents do, seeded once at startup. Every worker turn's very first action was, structurally, calling `.update()` on a document that had never existed.

I didn't take this on faith from reading the code. I reproduced it live: ran a real `spawn_worker_and_await` call against production Firestore and real Vertex AI, with the old code in place, and got back exactly the `NotFound` error the code read predicted — `404 No document to update: .../orgs/demo/agents/worker-07f9f4e34b`. Every spawned worker had been failing on its first turn, silently, since the feature shipped. The fix landed, I ran it again, and got a real successful reply back. Then I cleaned up the two test worker documents I'd created in the live `demo` org rather than leave test artifacts in production data.

The fix itself is small — a one-line `except NotFound: pass` in the one function every agent-status update already goes through, not a new Firestore document for every ephemeral worker (which would have polluted the persistent-agent roster the office floor actually renders). But finding it required reading a "boring," already-shipped function closely enough to notice what it assumed, rather than trusting that a feature which had been in the codebase for a while must have been exercised and confirmed working by now. It hadn't been — none of the existing tests exercised the real callback path; they all mocked it away.

## Finding three: the one check nobody could do from reading code

My own plan for this pass had explicitly flagged one item as unverifiable from code alone: whether the CEO's autonomous self-check trigger — a Cloud Scheduler job firing every 30 minutes, reviewing company state and escalating anything real — was actually doing what its prompt asked, rather than manufacturing busywork. That meant reading live production data after redeploying, not reading the trigger's code and calling it done.

It was firing correctly, every 30 minutes, for hours. And it had found something real — sort of. `list_tasks_tool()` was returning an empty list, and the CEO was reporting this, every single firing, as a broken tool: "Persistent Failure of Task Listing Tool," "Catastrophic Failure," "Total Loss of Task Visibility" — the language escalating each time, rewritten to sound more dire with each 30-minute cycle. I checked directly against Firestore: the demo org genuinely has zero tasks in it right now, because nobody had dispatched real work through the live product recently — an empty list was the *correct* answer, not a symptom of anything broken.

This is a subtler failure than the other two, and arguably a more interesting one: nothing crashed, nothing 404'd, the tool worked exactly as designed. The problem was the CEO's own judgment about what an empty result *means* — treating "no data yet" as equivalent to "the mechanism that fetches data is broken," and then, because the prompt said to escalate anything worth escalating, re-escalating the same (non-)finding with fresh dramatic wording every single cycle instead of recognizing a stable, previously-reported, unchanged situation for what it was. It was doing this to the company's own shared blackboard — the same Board tab I'd just built a frontend panel for as part of this pass, which meant a hackathon judge clicking around the live app could have opened it and seen a wall of increasingly alarming "CRISIS" language about a completely healthy system.

The fix lives in the trigger's own prompt, not in any tool: state plainly that an empty list is a normal, healthy result, not a failure to report; and that an unresolved finding which hasn't changed since the last check doesn't need to be re-alarmed with fresh urgency every 30 minutes. I cleared the stale board note and let the next scheduled firing write a calmer, accurate one.

## What came out of all that: closing the gaps for real

Once those two were fixed, the same audit had already surfaced a ranked list of real observability gaps — backend state that existed but was never rendered anywhere in the UI. I closed all of them, not just the cheap ones:

- **Verification votes, previously computed and thrown away.** `vote_aspects()` had always returned which individual checker passed or failed and why — Finance, Engineering, and Marketing's departments just never persisted it onto the task, only the final boolean. Now every one of those checkers' votes and reasons show up, expandable, on the task itself.
- **Worker execution trace**, which turned out to already half-exist by accident: the same session-ID-doubles-as-agent-ID mechanism behind the `NotFound` bug above meant a worker's trace subcollection write (a Firestore subcollection `.add()`, which — unlike `.update()` — doesn't require its parent document to exist) had been landing successfully all along. It just had no frontend panel reading it. Now it does, reusing the exact same `watchAgentTrace` function every registered agent's terminal view already used.
- **A live audit hash-chain status badge**, calling an endpoint that already existed ([`/api/org/{orgId}/audit/verify`](../../backend/app/api/audit.py)) but had never been wired to anything but a copy-pasteable curl example in the Commands tab.
- **A new Board tab**, for the CEO's shared blackboard collection, which had zero frontend surface of any kind before this.
- Previously invisible fields — which Gemini tier a task ran on, its attachment, its timestamps, an agent's session turn count — surfaced across the views that already had room for them.

## Connecting real integrations, and the app going blank mid-setup

With the eligibility fix live and the observability gaps closed, the last thing standing between this project and an actual recorded demo was making the "Connect with X" buttons — built weeks earlier, per ADR-0018, but never exercised against a real third-party account — actually work. That meant registering real apps on GitHub, Slack, and Notion, and it's where the final round of genuinely new bugs started.

The first attempt to connect GitHub landed on a bare JSON error page: `{"detail":"OAuth isn't configured yet (no oauth_state_secret set)"}`. Nothing wrong with the intent — `oauth_start` is deliberately a real top-level browser navigation, not a `fetch()` call, because it has to redirect the whole tab to the provider's consent screen, and a `fetch()` can't drive that. But that also means an `HTTPException` raised inside it doesn't show a nice in-app error — it leaves the browser sitting on a raw API response with the entire React app gone from the page. Which, from the outside, looked exactly like a second, unrelated bug: once I left that menu I had no way to get back to the main menu, and even Cmd+K didn't work. It wasn't a stuck menu. There was no app on that page at all to respond to Cmd+K — the tab had genuinely navigated away to a JSON blob. The fix was to check both `oauth_state_secret` and the target provider's client ID *before* ever leaving the SPA, and redirect back into the app with a `?oauth_error=` banner instead of raising — which also meant actually reading that query param on the frontend for the first time, since the *existing* callback error paths had been silently writing it into the URL and nothing had ever displayed it.

Getting Slack connected took two more rounds, both entirely outside this project's own code. A pasted Client ID that was one digit short of the real one (a screenshot OCR slip, not a typo I'd normally make) produced Slack's own "Invalid client_id parameter" — fixed by asking for the value freshly, typed directly off the live page rather than re-read from an earlier screenshot. Then, past that, a different Slack error: `invalid_team_for_non_distributed_app`. That one's a real Slack platform rule, not a bug anywhere in this codebase — a Slack app that hasn't gone through "Manage Distribution" can only be installed into the single workspace it was created under, and the workspace I was testing against wasn't that one. Nothing to fix in code; just the right workspace.

## Seeding a demo org for real, and finding the bugs a clean deploy can't show you

A working OAuth flow and a passing test suite don't prove a system behaves correctly under real, continuous use — they prove it behaves correctly the *first* time. So instead of just trusting the fixes, I dispatched a real goal to the live CEO agent — a new enterprise customer needing an invoice processed, an API incident investigated, and a welcome email and promo video drafted — through the actual production Pub/Sub path, and watched what a genuinely busy company floor surfaces that an empty one never will.

The first thing it surfaced was the exact same eligibility bug as ADR-0020, twice more, in places I hadn't checked. `shared/cross_model_check.py`'s independent-review checker and `app/services/compaction.py`'s session-summarizer both build their own raw `genai.Client()`, pinned to the old region, instead of going through the ADK default resolution the eligibility fix relied on — so upgrading the default model to a 3.5-tier model quietly broke both of them with a 404, in code I hadn't touched during the eligibility pass because neither file is an ADK `LlmAgent`. And because compaction was the thing failing, nothing was ever trimming the CEO's growing session — which is exactly how, a few hours into testing, its own session document hit Firestore's hard 1MiB cap and started failing every single turn outright.

Clearing that session and re-testing surfaced a second bug, self-inflicted this time: a Google-Search-grounded turn's event carried a raw SDK object nested somewhere inside its own "JSON-safe" dump — reproduced live, and since the exact shape depends on the real search response that came back, there was no one field to special-case around it. My first fix — stringify anything the JSON encoder chokes on — stopped that specific crash, but broke something else: `Event.model_validate()` on the read side expects a dict-or-`None` in that field, not a bare string, so the "fixed" write corrupted every later read of that same session. The actual fix converts the unencodable value to `None` instead — every field this can hit is genuinely Optional on ADK's own schema — and `get_session()` now also skips (and logs) any individual historical event that still fails validation for any other reason, so one bad event from any future bug can't brick an agent's whole memory the way this one briefly did.

Two more, both about media that looked "done" but wasn't actually usable. Break-room music (Lyria) turned out to be unconditionally broken on Cloud Run, independent of everything above — `generate_signed_url()` tries to sign locally using the credential's own private key by default, and neither Cloud Run's compute-engine credentials nor even a local `gcloud auth application-default login` credential have one, no matter that the IAM self-impersonation grant for exactly this case was already correctly in place from weeks earlier. And a Marketing task's "finished" promo video showed a black, unplayable box in its player — the Veo polling endpoint had been writing the video's raw `gs://` URI straight into the task, which no browser `<video>` tag can ever fetch, and never clearing the "still generating" flag either. Both got the identical real fix: hand the credential's own access token and service-account email to `generate_signed_url()` explicitly, so the call goes through the IAM `signBlob` API instead of trying (and failing) to sign locally — Google's own documented pattern for exactly this Cloud Run scenario, verified this time by actually fetching the resulting signed URL and confirming a real, playable video byte stream came back.

## The bug I found, twenty minutes before recording

The very last one wasn't caught by any audit. I caught it by clicking around the live app one more time before hitting record, the way an actual demo viewer would: clicking "Messages" on any agent instantly blanked the entire screen to white. No error toast, no console-visible crash message a non-developer would notice — just the whole app gone.

The cause, once found, was almost funny in how small it was. A message's `createdAt` field comes back from Firestore's `onSnapshot` as a real `Timestamp` *object*, not the string its own TypeScript interface claims — a quirk this codebase had already hit and solved once, with a small `toDisplayDate()` helper built specifically to coerce it safely. Nobody had reached for that helper in the one component rendering a message list, which instead handed the raw Timestamp object straight to React as a child. React doesn't tolerate rendering a bare object; it throws, and with no error boundary anywhere above it, the entire component tree unmounts. Three sibling spots — an agent's own `createdAt`, a task's `createdAt`, a board note's `updatedAt` — had the exact same bug, just quieter: `new Date(aTimestampObject)` doesn't throw, it silently returns "Invalid Date," which is how the agent detail header had been showing "active since Invalid Date" for a while without me flagging it as more than a cosmetic typo. All four now go through the one helper that already existed for exactly this.

That fix, the two media-signing fixes, and a freshly regenerated (and this time verified-playable) promo video all shipped and were confirmed live against production in the twenty minutes before the demo video was actually recorded.

## What I'd tell someone starting this project today

Write down why you rejected an alternative, not just what you chose — every one of the [twenty ADRs](../adr/) behind this project made a three-day pre-deadline audit tractable instead of terrifying, because I never had to re-derive whether an old decision still held; it was already on record. Verify against the real, live system before you trust anything that reads like a settled fact — a package's own docstring, a docs page, a "verified" code example someone else posted, or even your *own* earlier fix — this project hit that lesson nine separate times by the end (Gemma's Model Garden card, the Gemini-version eligibility gap, a silently-dead voice model, a Lyria field name a "verified" example got wrong, the twin verifier/compaction location bug, the session-corrupting first attempt at a JSON-safety fix, the break-room signing bug, the Veo unplayable-URL bug, and a raw Firestore Timestamp rendered straight into React), and every single time that discipline — actually calling the real API, actually reading the real error, actually fetching the resulting URL — was the only thing standing between "looks fine" and actually broken. Check what your own agents are actually saying to each other and to a human, not just whether the pipeline completes — the self-check trigger never crashed, never errored, and was still wrong in a way only reading its real output caught. And when a fix makes one symptom disappear, check the other side of that same boundary before calling it done — the write that stopped crashing and the read that then silently broke were two ends of the exact same pipe.

That's the whole story, as honestly as I can tell it — including the parts I got wrong the first time, and the one I didn't catch until I clicked the wrong button twenty minutes before the deadline. Thanks for reading.
