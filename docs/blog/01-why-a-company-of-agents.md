# Building Corporate, part 1: why a company of agents

*This is part 1 of a four-part series on building Corporate, a multi-agent web app for Google's [All Things Agentic](https://allthingsagentichackathon.devpost.com/) hackathon (track: The Fortified Enterprise Fleet, deadline 2026-08-31). This series is written for the hackathon submission — it's the full, unfiltered story: what I built, what I tried and threw away, and why, with no detail smoothed over for narrative convenience.*

If you read nothing else in this series, here's the shape of it: **part 1** (this post) is the five architectural bets I made before any real code existed, and why each alternative lost. **[Part 2](02-departments-verification-and-the-things-that-broke.md)** is what got built on top of that shape — nine department pipelines that all look different on purpose, the one rule that keeps an LLM's claims honest, and the first real production bugs a hardening pass turned up. **[Part 3](03-capability-expansion-and-the-roads-not-taken.md)** is two full research spikes that ended in "don't build this" (Google Antigravity, a mature open-source coding agent's own patterns) and the capability expansion — sub-agent spawning, a sandboxed code-execution tool, realtime voice, OAuth, and a model that turned out not to exist where I'd assumed it did. **[Part 4](04-the-final-72-hours.md)** is the ending: a hard eligibility gap found three days from the deadline, and — because I went looking instead of assuming a clean deploy meant a clean system — nine more real, previously-invisible bugs found and fixed in the final 72 hours, including one caught by a single click twenty minutes before the demo video was recorded. Start here for the "why"; read straight through for the whole arc.

## The shape question, before any code

The Fortified Enterprise Fleet track's own description is specific: "scalable institutional agent networks" with real components for discovery/lifecycle, execution/state management, security/governance, and telemetry, emphasizing "production compliance and cross-department deployment." That phrase — *cross-department* — is doing real work. It's not asking for one clever agent; it's asking for an organization.

So before writing a line of application code, the first real decisions I made were about shape, not features:

**Hosted, not desktop** ([ADR-0001](../adr/0001-cloud-native-hosted-architecture.md)). An early direction modeled Corporate as a local app that spawns agent processes on the user's own machine, with a thin cloud-sync layer bolted on just to technically touch Google Cloud. I rejected this outright. The hackathon needs a real hosted URL and load-bearing Google Cloud usage — Firestore, Pub/Sub, and Cloud Run doing the actual work, not sitting off to the side as a sync target. A "desktop for local dev, cloud for the submission" hybrid was also on the table briefly; rejected as duplicated effort with no feature it would actually unlock.

**One language, one framework, for the whole backend** ([ADR-0002](../adr/0002-unify-backend-on-python-fastapi-adk.md)). Each department could, in principle, pick whatever language and agent framework fit its own problem best — a fraud-detection pipeline in one stack, a customer-support classifier in another. I rejected this too. A coherent, single stack (Python, FastAPI, [Google ADK](https://github.com/google/adk-python) 2.7.1) scores better against "Architectural Discipline" than a patchwork of five different runtimes would, and it means one contributor — or one Claude Code session picking this project back up — can actually read and reason about the whole system, not just their own corner of it.

**Firestore for state, Pub/Sub for messaging — not Firestore doing both** ([ADR-0003](../adr/0003-firestore-pubsub-for-state-and-messaging.md)). A pure-Firestore design, where each agent polls its own "inbox" collection for new messages, was seriously considered. I rejected it: polling doesn't fit Cloud Run's request-driven scaling model — you either waste cost keeping instances warm to poll frequently, or you accept real latency between a message landing and an agent noticing it. Pub/Sub push, one topic (`agent-bus`) with one filtered subscription per agent, won instead. And within that: whether an agent's own judgment should decide if a reply is "owed," or whether that should be mechanical. I chose mechanical — `publish_message()` is the one function that increments a hop counter and derives `requires_reply` from the message's `act` field, and a hard cap (`hops > 12`) kills a runaway conversation and flags it for a human, no LLM ever gets a vote in whether this particular safety mechanism fires.

**A2A at the boundary, never internally** ([ADR-0004](../adr/0004-a2a-scoped-to-external-boundary-only.md)). ADK ships first-class [A2A (Agent2Agent) protocol](https://a2a-protocol.org/) support, and it would technically be possible to route all internal CEO-to-department messaging over it. I rejected that specifically — there's no external, cross-vendor, opaque-agent problem to solve *inside* the company, and A2A's request/response shape is a worse fit for Cloud Run's push/fan-out model than Pub/Sub already is for that internal traffic. But I didn't drop A2A either: Sales & CRM is exposed as a real, standalone A2A server, its own Cloud Run service with its own `/.well-known/agent-card.json`, for genuinely external callers. That's the actual "Fortified Enterprise Fleet" trust-boundary story — a clear, deliberate seam between internal machinery and the outside world, not a protocol adopted everywhere just because it exists.

**One contract, not nine bespoke integrations** ([ADR-0005](../adr/0005-department-contract-and-scaffolding.md)). The alternative to a shared department contract is each department wiring its own Firestore reads, its own Pub/Sub publish calls, its own audit logging, as needed. I rejected that as exactly the "everyone reinvents their own plumbing" failure mode a shared contract exists to prevent. Every department is a Python package exporting a `DepartmentSpec` and one function, `on_task_received(org_id, task) -> TaskResult` — the *only* entrypoint the platform ever calls, wrapped automatically in `@audited_task` for hash-chained audit logging and failure containment. A new department gets idempotent dispatch, tamper-evident logging, and "never crash, always reply" failure handling for free, on day one, with zero of its own code.

## What this bought me later

Every one of those five decisions reads, in hindsight, like an obvious call. They didn't feel obvious in the moment — the polyglot-department idea and the A2A-everywhere idea both had real, articulable arguments in their favor. What made the eventual call tractable wasn't confidence, it was writing down the alternatives that lost and *why*, in an ADR, before moving on. [Twenty ADRs](../adr/) later (the count as of this writing), that discipline is the reason a three-days-to-deadline audit pass — covered in [part 4](04-the-final-72-hours.md) of this series — was a tractable few days of focused work instead of a panic. You can't safely re-derive whether a decision still holds if you never wrote down why it was made.

[Part 2](02-departments-verification-and-the-things-that-broke.md) covers what got built on top of that shape: the department pipelines themselves, the verification patterns that keep an LLM's claims honest, and the real production bug I found in a supposedly working feature.
